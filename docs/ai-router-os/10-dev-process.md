# 10. 開発ルール・承認フロー(要件⑩)

## 1. 開発サイクル(全フェーズ共通・省略不可)

```
① 設計    設計ドキュメント(docs/ai-router-os/ 配下)を作成/更新
   ↓
② レビュー 設計レビュー(Reviewer Agent の自動レビュー + オーナー承認)
   ↓      ★ オーナー承認なしに ③ へ進まない ★
③ 実装    ブランチ作成 → 実装(Claude Code)→ セルフレビュー
   ↓
④ テスト   ユニット(分類・ルーティング・価格計算)+ E2E(代表パイプライン)+ コスト実測
   ↓
⑤ ドキュメント README / 設計docの実装反映 / 運用手順(SOP として Vault にも保存)
   ↓
⑥ 改善提案 実装中に見つけた課題・次フェーズへの提案を明文化(Reviewer Agent + 人間)
```

## 2. 承認フロー(オーナー承認が必要なポイント)

| タイミング | 承認内容 | 方法 |
|---|---|---|
| 各フェーズ開始前 | 設計ドキュメント | このリポジトリの PR コメント or チャットで「承認」 |
| 外部発信 | SNS投稿・口コミ返信(運用時) | Dashboard 承認キュー or LINE |
| コスト影響 | 日次上限変更・新規有料API導入 | 明示的な承認 |
| 経営判断 | CEO Agent の提案の採否 | 判断ログに人間の決定を記録 |

## 3. 実装規約

- ブランチ: `claude/<topic>` / コミット: 変更目的を1行目に(日本語可)
- 型安全: TypeScript strict。API入出力は zod でバリデーション(導入済み)
- モデルID・価格・上限値はハードコード禁止 → `lib/router/models.ts` / `pricing.ts` に集約
- シークレットは `.env.local`(コミット禁止)。n8n/webhook は署名検証必須
- テスト: 分類はゴールデンケース20件(依頼文→期待ルート)を fixtures 化し、リグレッション検知

## 4. 品質ゲート(QA Agent / Reviewer Agent)

- **実装前**: Reviewer Agent が設計docをレビュー(矛盾・漏れ・コスト影響)→ 結果をオーナーに添えて承認依頼
- **実装後**: `npm run lint` + `tsc --noEmit` + テスト + コスト実測値と見積の乖離チェック(±30%超で警告)
- **運用中**: QA Agent が発信物を事前チェック、Reviewer Agent が週次改善提案(07参照)
